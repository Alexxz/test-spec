# Spec Delta

## Purpose

Доступ к созданию записей и поиску через визуальный пользовательский интерфейс и программный API с одинаковыми правилами обработки данных.

## ADDED Requirements

### Requirement: Визуальный интерфейс

Система MUST предоставлять визуальный интерфейс в браузере для ввода имени и телефона, создания записи и отдельного поиска по имени или телефону. Интерфейс MUST показывать все полученные результаты, пустой результат и ошибки понятными сообщениями.

#### Scenario: Создание через интерфейс
- **WHEN** пользователь заполняет имя и телефон и отправляет форму создания
- **THEN** при успешной записи интерфейс показывает подтверждение

#### Scenario: Поиск через интерфейс
- **WHEN** пользователь выбирает поиск по имени или телефону и вводит корректный запрос
- **THEN** интерфейс показывает найденные имена и телефоны либо сообщение об отсутствии совпадений

#### Scenario: Ошибка ввода
- **WHEN** пользователь отправляет неверные данные
- **THEN** интерфейс показывает причину ошибки и не сообщает об успешном создании

### Requirement: Программный доступ

Система MUST предоставлять документированный HTTP API с JSON для создания записи и поиска по каждому полю. API MUST возвращать структурированные результаты и различать неверные входные данные, отсутствие совпадений и ошибку хранения. Контракт запросов и ответов указан в design.md, раздел «HTTP API».

#### Scenario: Вызов из программы
- **WHEN** программа создаёт корректную запись через API и затем ищет её по каждому полю
- **THEN** создание возвращает идентификатор, а оба поиска включают созданную запись

#### Scenario: Различимые исходы
- **WHEN** программа отправляет неверный ввод, корректный поиск без совпадений или запрос, завершившийся ошибкой хранения
- **THEN** API позволяет программно различить эти три исхода без разбора текста для человека

### Requirement: Общие данные и правила

Визуальный интерфейс и API MUST работать с одним набором записей и применять требования directory-records одинаково.

#### Scenario: Запись через API видна в интерфейсе
- **WHEN** API подтвердил создание записи и пользователь выполняет соответствующий поиск в интерфейсе
- **THEN** результат включает эту запись

#### Scenario: Запись через интерфейс видна в API
- **WHEN** интерфейс подтвердил создание записи и программа выполняет соответствующий поиск через API
- **THEN** результат включает эту запись

### Requirement: Время поиска на проверочном объёме

Система MUST отображать полный результат каждого поиска не позднее одной секунды после отправки формы при проверке на 10 000 записях одним локальным пользователем по методике из design.md. Этот объём MUST NOT быть программным ограничением числа записей.

#### Scenario: Проверка скорости
- **WHEN** на эталонной машине выполняется проверочный набор из раздела «Проверка производительности» design.md
- **THEN** каждый поиск завершается отображением полного результата за время не более 1 000 мс
- **THEN** отчёт содержит характеристики машины, версии ПО и измерения

#### Scenario: Превышение проверочного объёма
- **WHEN** в справочнике уже есть 10 000 записей и пользователь создаёт ещё одну корректную запись при доступном месте на диске
- **THEN** запись принимается и доступна при поиске; гарантия времени ответа за пределами проверочного объёма не установлена

### Requirement: Доступность правил ввода

Интерфейс MUST до отправки показывать правила телефона, точное совпадение и учёт регистра имени при поиске. Отображённые имена и телефоны MUST быть доступны для выделения и копирования стандартными средствами браузера.

#### Scenario: Пользователь видит ограничения заранее
- **WHEN** пользователь открывает форму создания или выбирает поиск по имени либо телефону
- **THEN** соответствующие подсказки доступны до отправки запроса
- **THEN** они соответствуют правилам directory-records

#### Scenario: Использование найденного номера
- **WHEN** результат поиска содержит телефон с плюсом или ведущими нулями
- **THEN** пользователь может выделить и скопировать его полное отображённое значение без преобразования

### Requirement: Продолжение после ошибки

Интерфейс MUST сохранять введённые значения при ошибке создания или поиска и MUST позволять исправить их и отправить запрос снова без перезагрузки страницы. Сообщение MUST различать ошибку ввода, недоступность операции и отсутствие совпадений.

#### Scenario: Исправление телефона
- **WHEN** создание отклонено из-за неверного телефона
- **THEN** имя и телефон остаются в форме, показано объяснение ошибки
- **THEN** пользователь может исправить телефон и успешно сохранить запись

#### Scenario: Повтор после ошибки поиска
- **WHEN** поиск завершился ошибкой связи или хранилища
- **THEN** запрос сохраняется, показано сообщение о невозможности выполнить поиск вместо сообщения об отсутствии совпадений
- **THEN** после восстановления доступности пользователь может повторить поиск

### Requirement: Состояние и актуальность поиска

Интерфейс MUST показывать состояние выполнения поиска и MUST скрывать результаты предыдущего запроса при отправке нового. Пока поиск не завершён, новая отправка из формы поиска MUST быть недоступна. Ошибка MUST NOT представляться как успешный результат.

#### Scenario: Новый поиск после успешного
- **WHEN** после найденной записи пользователь отправляет другой поисковый запрос
- **THEN** прежние результаты скрываются и отображается состояние поиска
- **THEN** после завершения показывается только результат либо ошибка нового запроса

### Requirement: Подтверждение и неопределённость сохранения

Интерфейс MUST показывать состояние сохранения и предотвращать повторную отправку формы до завершения запроса. Успех MUST показывать сохранённые имя и телефон. Потеря ответа MUST сообщаться как неопределённый исход без автоматического повтора; введённые поля MUST сохраняться для проверки поиском.

#### Scenario: Повторное нажатие во время сохранения
- **WHEN** пользователь повторно пытается отправить форму, пока первый запрос ещё выполняется
- **THEN** второй POST не отправляется
- **THEN** после завершения форма снова доступна; явная новая отправка является новой операцией

#### Scenario: Ответ не получен
- **WHEN** ответ на создание потерян или истёк срок ожидания
- **THEN** интерфейс сообщает, что не удалось подтвердить сохранение, и предлагает проверить данные поиском
- **THEN** автоматического POST нет и сообщение не утверждает, что запись отсутствует

#### Scenario: Успешное подтверждение
- **WHEN** API подтвердил создание пары с окружающими пробелами
- **THEN** интерфейс показывает сохранённые значения после удаления окружающих пробелов
