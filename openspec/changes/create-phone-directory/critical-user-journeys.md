# Critical User Journeys первой версии

## Зачем этот документ

Critical User Journey (CUJ) — путь к результату, который особенно важен для пользователя или часто повторяется. В этом подходе мы спрашиваем «смог ли человек найти нужный телефон?», а затем проверяем все необходимые шаги, включая сбои.

Пример из Google SRE: пользовательский путь состоит из нескольких задач, и проверка отдельных технических показателей может пропустить сбой общего результата. [Источник: Modeling User Journeys](https://sre.google/workbook/implementing-slos/).

Этот файл — наше дополнение к OpenSpec, а не обязательный встроенный тип документа. Нормативные правила находятся в `specs/`; здесь — цели, пути и связь с проверками. Поскольку интервью и наблюдений за пользователями не было, выбор критических путей основан на исходных требованиях и нашем обсуждении, а не на измеренной частоте использования.

## Пользователь и приоритеты

Основной пользователь — человек, ведущий локальный справочник. Ему нужно сохранить контактные данные и позже получить верное соответствие имени и телефона. Второй способ использования — программа, обращающаяся к тем же данным через API.

Все пути ниже обязательны для приёмки. Порядок отражает предлагаемую важность: сначала основной поиск, затем создание и доверие к сохранению. Восстановительные ветви проверяются так же, как обычное успешное прохождение.

| ID | Цель | Почему путь критичен | Успешный результат |
| --- | --- | --- | --- |
| CUJ-1 | Найти телефон по известному имени | Основная причина пользоваться справочником | Показаны все соответствующие записи либо явно сообщено об отсутствии совпадений |
| CUJ-2 | Узнать имя по известному номеру | Вторая основная операция исходных требований | Показаны все связанные имена без потери общего номера |
| CUJ-3 | Сохранить контакт и убедиться, что он доступен | Без этого справочник нельзя пополнять и ему нельзя доверять | Подтверждённая запись находится по обоим полям |
| CUJ-4 | Вернуться к данным после закрытия или сбоя | Потеря подтверждённых данных разрушает ценность продукта | Прежние записи и ID доступны после запуска с тем же хранилищем |
| CUJ-5 | Использовать справочник из другой программы | Программный доступ явно требуется | Клиент создаёт запись, находит её и различает ошибки и пустой результат |

## CUJ-1: Найти телефон по имени

**Контекст:** приложение запущено, человек знает имя в сохранённом написании. В тестовых данных есть имя с несколькими телефонами.

1. Открывает страницу и видит способ поиска и подсказку о точном совпадении с учётом регистра.
2. Выбирает поиск по имени, вводит имя и отправляет запрос.
3. Видит состояние выполнения; прежний результат больше не представлен как ответ на этот запрос.
4. Получает все совпадения с именами и телефонами. Номер можно выделить и скопировать обычными средствами браузера.

**Приёмка:** нет пропущенных совпадений и посторонних записей; полный результат отображается за одну секунду по методике design.md. Путь измеряется от отправки формы до результата, а не включает время чтения и набора пользователем.

**Ветви:**
- Пустой запрос → понятная ошибка, строка ввода сохраняется, можно исправить и отправить снова.
- Вставка имени с табуляцией, переносом строки или другим запрещённым символом → понятное сообщение об однострочном имени; прежнее значение остаётся, строки не склеиваются.
- Совпадений нет → отдельное сообщение «ничего не найдено», а не ошибка.
- Хранилище или связь недоступны → сообщение «не удалось выполнить поиск», без утверждения об отсутствии записей; запрос сохраняется для повтора.
- Новый запрос дал ошибку → результаты прежнего поиска скрыты, а не подписаны новым запросом.

## CUJ-2: Найти имя по номеру

**Контекст:** человек располагает номером в поддерживаемом формате; в данных есть общий номер у двух имён и номер с ведущими нулями.

1. Открывает страницу, выбирает поиск по телефону.
2. Видит подсказку о допустимом формате, вводит номер и запускает поиск.
3. Получает все связанные записи; плюс и ведущие нули сохранены.

**Приёмка:** общий номер возвращает оба имени; `00123` не превращается в `123`; HTTP-кодирование не превращает плюс в пробел. Для браузера действует тот же предел времени, что в CUJ-1.

**Ветви:** неподдерживаемое форматирование → объяснение допустимого формата с сохранением ввода; отсутствие совпадений и недоступность поиска различаются как в CUJ-1.

## CUJ-3: Сохранить и проверить контакт

**Контекст:** человек хочет сохранить новую пару имени и телефона. Для проверок неопределённого исхода используются свежие значения, которых до операции не было.

1. Открывает форму и видит правила имени и телефона до отправки: имя в одну строку без управляющих символов, телефон в указанном формате.
2. Вводит пару и нажимает сохранение.
3. Пока запрос выполняется, видит состояние сохранения; повторное нажатие не отправляет ещё один запрос.
4. После успешной фиксации видит сохранённые имя и телефон, включая удаление пробелов по краям.
5. Находит запись по имени и телефону и сверяет значения.

**Приёмка:** обычное однократное действие создаёт ровно одну запись; явно повторённая операция после завершения может создать дубликат согласно directory-records. Сообщение об успехе означает, что фиксация в хранилище завершилась.

**Ветви:**
- Ошибка ввода → поля сохраняются; после исправления можно завершить тот же путь.
- Подтверждённая ошибка хранения → нет сообщения об успехе; поля сохраняются; после устранения причины пользователь может повторить действие.
- Потеря ответа, включая начало ответа с незавершённым JSON-телом → сообщение «не удалось подтвердить сохранение», а не утверждение «запись не сохранена»; автоматического повтора нет. Пользователь может искать по введённым значениям.

**Ограничение:** если такая же пара существовала раньше, её наличие в поиске не доказывает, что именно последний запрос завершился успешно. В первой версии нет ключа идемпотентности — идентификатора операции, позволяющего безопасно повторить её без создания второй записи. Не обещаем гарантированно однократное создание при потере ответа; это возможное отдельное улучшение.

## CUJ-4: Вернуться к сохранённым данным

**Контекст:** создание нескольких записей подтверждено, известен путь файла хранилища.

1. Пользователь завершает приложение либо процесс аварийно прекращает работу.
2. Запускает его по инструкции с тем же файлом.
3. Открывает страницу, ищет по имени и телефону.
4. Получает прежние значения; API возвращает прежние ID.

**Приёмка:** все подтверждённые записи сохранены. При сбое незавершённого создания нет частичной записи, а старые записи доступны. Проверки сбоя выполняются управляемо по design.md, а не вручную на пользовательском файле.

**Ветви:** неверный путь, несовместимость схемы, ошибка integrity_check или невозможность открыть существующую БД → понятная ошибка запуска; существующий файл не удаляется и не заменяется пустой БД. Если по явно заданному новому пути файла нет, создаётся новое хранилище; инструкция предупреждает, что это отдельный справочник.

**Граница:** отключение питания, потеря диска и резервные копии не включены в гарантии первой версии.

## CUJ-5: Работать через API

**Контекст:** другая программа знает локальный адрес приложения и контракт API.

1. Выполняет документированный POST с именем и телефоном.
2. Получает `201`, ID и сохранённые значения.
3. Выполняет оба GET; каждый результат содержит ID созданной записи.
4. Для отсутствующего значения получает `200` и пустой список; неверный ввод и ошибку хранения различает по статусу и коду.

**Приёмка:** примеры из документации воспроизводимы, API и браузер видят один набор данных. При потерянном ответе POST клиенту не обещается безопасный автоматический повтор; это описано рядом с примером создания.

## Что изменилось после разбора

| Пробел | Решение | Где закреплено |
| --- | --- | --- |
| Успешный POST ещё не доказывает, что пользователь позже найдёт запись | Связать создание, оба поиска и перезапуск | CUJ-3–4; задачи 5.3 и 6.4 |
| Сообщение об ошибке не позволяло явно продолжить путь | Сохранять ввод, разрешать исправление и повтор | directory-access: «Продолжение после ошибки» |
| Ошибку поиска можно спутать с отсутствием совпадений | Разные сообщения, скрытие устаревшего результата | directory-access: «Состояние и актуальность поиска» |
| Повторное нажатие могло случайно создать дубликат | Один незавершённый запрос создания от формы | directory-access: «Подтверждение и неопределённость сохранения» |
| Путь поиска обещал найти контакт, но точные правила могли быть неизвестны | Видимые подсказки о точном поиске и формате | directory-access: «Доступность правил ввода» |
| Поиск такой же пары после потери ответа не доказывает успех последней операции | Явно описать ограничение, не обещать идемпотентность | CUJ-3; design.md и инструкция API |

CUJ не заменяет проверки каждого требования. Итоговый отчёт должен отдельно показать прохождение полного пути и его восстановительных ветвей, а не только число прошедших отдельных тестов. Сейчас выполнен анализ документов; сами пути ещё не запускались, поскольку реализации нет.

## Вопросы удобства для следующих изменений

Точное совпадение имени с учётом регистра и телефон без пробелов и дефисов могут мешать обычному пользователю. Пока сохраняем уже принятые правила и объясняем их в интерфейсе. Поиск без учёта регистра, нормализация номера и безопасный повтор создания после потери ответа потребуют отдельного пересмотра требований, а не скрытой правки при реализации.

## Уточнения после LLM-expert review

После экспертного разбора CUJ-1 и CUJ-3 используют однострочное имя по ADR-0006. В CUJ-3 срок ожидания охватывает всё тело ответа, в CUJ-4 проверяется структурная целостность SQLite при запуске. Методика скорости уточнена в design.md; источники и решения находятся в llm-expert-review.md. Реальные прохождения этих ветвей ещё предстоят.
