# Proposal

## Why

Нужна система хранения имён и телефонов с поиском в обоих направлениях, визуальным интерфейсом и программным доступом. Исходные требования нельзя однозначно проверить: «хорошая», «надёжно» и «много» пока не задают критериев приёмки — условий, по которым можно решить, выполнена ли работа.

## What Changes

- Описать создание записи и точный поиск имени по телефону и телефона по имени.
- Определить одинаковое поведение графического интерфейса и API.
- Задать проверку отображения результатов поиска за одну секунду на наборе из 10 000 записей.
- Описать сохранение данных после перезапуска и поведение при ошибках записи.
- Отдельно зафиксировать допущения и вопросы, которые исходный текст не разрешает.
- Описать критические пользовательские пути создания, поиска, возвращения к данным и программного доступа, включая восстановление после ошибок.
- В первой итерации использовать SQLite; собственный движок БД рассматривать как возможное последующее расширение.

Статус: **подготовлено к итоговому просмотру перед реализацией**. Правила данных приняты без замечаний; технические детали и методика проверки дополнены при продолжении работы над спецификацией. Происхождение решений отмечено в `review.md`. Реализация не начата.

## Capabilities

### New Capabilities

- `directory-records`: запись пар «имя — телефон» и поиск в обоих направлениях.
- `directory-access`: графический и программный доступ к операциям справочника.
- `durable-storage`: сохранность подтверждённых записей при перезапуске и сбое процесса.

### Modified Capabilities

Нет: существующих спецификаций и реализации нет.

## Impact

Создаются только документы. Для первой итерации согласовано хранение в SQLite — готовой SQL СУБД (системе управления базами данных). Для приложения выбраны Python, визуальный интерфейс в браузере и HTTP API с JSON; пользователь оставил этот выбор на наше усмотрение. Разработка собственного движка БД возможна в последующих итерациях, но не входит в текущий объём. Прикладные правила справочника следует отделить от реализации хранения, чтобы будущая замена не требовала их переписывания. Технические решения описаны в `design.md`, сквозные пользовательские цели и ветви восстановления — в `critical-user-journeys.md`.

Объём первой версии по принятому черновику: один пользователь на одной машине, создание и поиск записей. Изменение, удаление, импорт, экспорт, учётные записи и работа через Интернет пока не включены и требуют отдельного обсуждения.
