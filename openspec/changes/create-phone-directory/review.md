# Разбор требований и решений

## Как читать документы

Спецификация описывает наблюдаемое поведение, а технический проект `design.md` — устройство реализации. Capability в OpenSpec — отдельная возможность системы; delta spec — изменение её требований. Здесь все возможности новые и перечислены под `ADDED Requirements`.

`MUST` означает обязательное требование. Scenario — проверяемая ситуация: `WHEN` задаёт условие, `THEN` — ожидаемый результат. `tasks.md` содержит шаги реализации; пустой флажок означает, что шаг ещё не выполнен.

## Происхождение решений

- **Прямое уточнение пользователя:** первая итерация использует SQLite; в перспективе возможны собственные приложение и движок БД.
- **Прямое уточнение пользователя:** масштаб — тысячи записей.
- **Выбор при отсутствии предпочтений пользователя:** Python, браузер и HTTP API с JSON.
- **Правила исходного черновика:** пользователь прочитал документы и сообщил, что замечаний нет; сохраняем правила данных, поиска и границы первой версии ниже.
- **Предложенный ориентир после обсуждения масштаба:** 10 000 записей и результат поиска за одну секунду. После просьбы продолжить этот ориентир принят для подготовки итогового пакета; точную методику, эталонное окружение и технические детали выбрал автор документов. Отдельного ответа «да» на каждую деталь методики пользователь не давал.
- **Технические решения автора:** Flask, схема таблицы, настройки SQLite, контракт HTTP, обработка ошибок и план проверки. Обоснования и альтернативы находятся в design.md; это проект реализации, а не описание уже написанного кода.

## Правила первой версии

| ID | Правило | Причина |
| --- | --- | --- |
| A1 | Одна запись содержит одно имя и один телефон, у неё постоянный уникальный ID | Одинаковые имена не означают одного человека |
| A2 | Несколько телефонов одного имени, один телефон нескольких имён и повтор пары допустимы | Нет искусственного запрета на совпадения |
| A3 | Поиск точный с учётом регистра после удаления окружающих пробелов U+0020 | Однозначно проверяемая семантика |
| A4 | Телефон — строка из необязательного плюса и 1–15 цифр ASCII | Сохраняются ведущие нули, не угадываются страна и правила набора |
| A5 | Один локальный пользователь; создание и поиск | Ограниченный объём первой итерации |
| A6 | Подтверждённые записи переживают перезапуск и сбой процесса на исправном диске | Конкретная гарантия сохранности |
| A7 | Пустой поисковый запрос — ошибка; отсутствие совпадений — успешный пустой список | Различаются неверный ввод и отсутствие данных |

Изменение, удаление, импорт, экспорт, доступ через Интернет, учётные записи, отключение питания, потеря диска и резервное копирование не входят в первую итерацию. Эти возможности можно добавить отдельными изменениями OpenSpec.

## Состояние вопросов

| Вопрос | Решение |
| --- | --- |
| Q1: свой движок или готовая СУБД? | SQLite сейчас; свой движок возможен позднее |
| Q2: язык? | Python |
| Q3: правила данных и поиска? | A1–A4 и A7, приняты без замечаний |
| Q4: объём и надёжность? | Границы исходного черновика A5–A6 сохранены |
| Q5: масштаб и скорость? | Тысячи записей; выбран критерий 10 000 записей / 1 секунда, методика в design.md |
| Q6: интерфейс и API? | Браузер, HTTP с JSON; контракт в design.md |

Вопросов, препятствующих составлению задач первой версии, не осталось. Версии зависимостей фиксируются и проверяются при подготовке окружения, без изменения внешнего поведения.

## Уточнения после разбора Critical User Journey

Пути CUJ-1–5 описаны в `critical-user-journeys.md`. Это дополнительный документ проекта. Он помог выявить и закрыть пробелы в подсказках, продолжении после ошибки, актуальности результатов и подтверждении сохранения. Новые нормативные требования добавлены в directory-access; техническое поведение и задачи обновлены одновременно.

Выбор этих путей основан на требованиях, без пользовательского исследования. Новые детали предложены при доработке: сохранение ввода, видимое состояние запросов, блокировка повторной отправки одной формы, срок ожидания браузера 5 секунд. Последний не заменяет проверку успешного поиска за одну секунду. Правила точного поиска, формата телефона и разрешение на дубликаты сохранены.

Остаточное ограничение: после потери ответа на создание поиск уже существующей пары не позволяет узнать исход именно последнего запроса. Это явно описано; идемпотентность (безопасный повтор операции без дополнительного эффекта) пока не добавлена. Также точное написание имени и номера может быть неудобным; изменение семантики оставлено отдельной доработкой.

## Что дальше

Итоговый просмотр новых технических деталей, затем реализация по `tasks.md`. Сейчас все флажки пустые, поскольку написаны только документы. После реализации нужно выполнить проверки поведения, сохранности и скорости, а уже затем архивировать изменение. При архивации новые требования объединяются с основными спецификациями в `openspec/specs/`.
