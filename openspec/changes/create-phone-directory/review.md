# Разбор исходных требований

## Как читать этот черновик

Спецификация — описание наблюдаемого поведения: что пользователь вводит и какой результат получает. Она позволяет проверить реализацию, не привязываясь к устройству кода.

В OpenSpec capability означает отдельную возможность системы. Delta spec описывает предлагаемые изменения; здесь все возможности новые, поэтому используются разделы `ADDED Requirements`. `MUST` означает обязательность внутри предлагаемого контракта, а не то, что черновик уже согласован. Scenario — конкретный проверяемый пример: `WHEN` задаёт действие или условие, `THEN` — ожидаемый результат.

## Связь с исходным текстом

| Исходное требование | Где отражено | Что необходимо уточнить |
| --- | --- | --- |
| «Хорошая база данных» | Конкретные требования во всех трёх спецификациях | Какие свойства важнее: удобство, скорость, сохранность? Само слово «хорошая» не является проверкой |
| «Визуальный интерфейс и API» | `specs/directory-access/spec.md` | Какой интерфейс нужен: браузер или отдельное настольное окно? Как программы обращаются к системе? |

| «Имена по телефону» | `specs/directory-records/spec.md` | Точное совпадение или поиск по части номера? |

## Согласованные решения

**D1 — хранение по итерациям.** По уточнению пользователя первая итерация использует SQL БД SQLite. SQL — язык запросов к данным; SQLite — готовая СУБД, которую можно встроить в приложение. В перспективе задача может включать и приложение, и собственный движок БД. Это возможность дальнейшего развития, а не обязательство реализовать движок сейчас.

Прикладные правила — например, что считать совпадением имени — описываем независимо от SQLite. Техническую границу между приложением и хранилищем фиксируем в `design.md`. Замена движка в будущем потребует отдельного решения о переносе существующих данных и проверки тех же требований к поведению.

## Предлагаемые допущения

Это решения автора черновика, а не факты из исходного текста.

| ID | Предложение | Зачем оно нужно |
| --- | --- | --- |
| A1 | Одна запись содержит одно имя и один телефон; у записи есть постоянный уникальный ID | Одинаковые имена не означают одного человека; ID позволяет различать записи |
| A2 | Несколько телефонов одного имени и один телефон нескольких имён допустимы; повтор пары тоже допустим | Не вводим запрет, которого нет в исходном тексте; защиту от случайного повтора можно обсудить |
| A3 | Поиск точный и с учётом регистра после удаления пробелов по краям; без поиска по части строки | Это простое и однозначно проверяемое начало |
| A4 | Телефон — строка из необязательного `+` и 1–15 цифр ASCII; форматирование и проверка реального существования номера не входят в первую версию | Сохраняются ведущие нули; не угадываем страну и правила набора |
| A5 | Один пользователь, одна машина; первая версия поддерживает создание и поиск | Ограничивает объём учебной задачи |
| A6 | Подтверждённая запись переживает штатный перезапуск и аварийное завершение процесса на исправном диске | Конкретизирует часть слова «надёжно»; отключение питания и потеря диска пока не покрыты |
| A7 | Пустой поисковый запрос считается ошибкой, отсутствие совпадений — успешным пустым результатом | Различает неверный ввод и отсутствие данных |

## Вопросы перед завершением спецификации

1. **Q1 — решён для первой итерации:** используем SQLite (D1). Границы библиотек для возможного собственного движка определим при планировании той итерации.
2. **Q2:** какой язык программирования выбрать? Это ограничение реализации; поведение поиска от языка не зависит.
3. **Q3:** подходят ли A1–A4 и A7? Нужны ли несколько телефонов внутри одного контакта, запрет повторов, поиск без учёта регистра или нормализация телефонного номера — приведение разных записей одного номера к единому виду?
4. **Q4:** подходят ли A5–A6? Нужны ли изменение, удаление, одновременные пользователи, доступ по сети или восстановление из резервной копии?
5. **Q5:** что означает «много»: сколько записей, какой размер имени, сколько одновременных запросов? Для какого оборудования и какого времени ответа задаём критерии? До ответа требование вместимости и производительности **не завершено**.
6. **Q6:** визуальный интерфейс в браузере или настольное приложение? API — HTTP с JSON (запросы по сети и структурированный текст) или библиотека, вызываемая из программы?

Пример формы критерия производительности, не готовое требование: «При N записях на машине с характеристиками H не менее 95% поисков укладываются в T миллисекунд при C одновременных запросах». Значения N, H, T и C нужно выбрать, а затем проверить измерением. Процентиль p95 — порог, в который укладываются 95% измерений.

## Что дальше

Сначала уточнить оставшиеся вопросы и обновить черновик. В `design.md` уже зафиксировано согласованное направление хранения; остальные технические решения пока открыты. После их определения создать `tasks.md` с проверяемыми шагами реализации.

После реализации и проверки изменение можно архивировать: OpenSpec переносит завершённое изменение в архив и объединяет его требования с основными спецификациями в `openspec/specs/`. Сейчас там нет описания готового продукта.
