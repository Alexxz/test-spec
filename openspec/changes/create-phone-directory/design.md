# Design

## Context

Проект находится на стадии уточнения требований. Реализации нет. Пользователь согласовал SQLite для первой итерации и допускает создание собственного движка БД в будущем. Документ фиксирует это решение, но пока не является полным техническим проектом.

## Goals / Non-Goals

- Первая итерация: приложение справочника с хранением в SQLite.
- Отделить правила справочника от кода доступа к SQLite.
- Разработку собственного движка, поддержку нескольких движков одновременно и перенос данных между ними оставить для последующих решений.

## Decisions

### D1: SQLite в первой итерации

Использовать готовую SQL СУБД SQLite. Это позволяет сначала проверить поведение приложения и освоить процесс работы со спецификацией, не добавляя одновременно разработку движка хранения. Альтернатива — сразу создавать собственный движок — существенно расширяет текущую задачу и отложена пользователем.

SQLite является техническим выбором, поэтому он фиксируется здесь, а требования к видимому поведению остаются в `specs/`.

### D2: Отдельная граница доступа к хранилищу

Предлагаемое архитектурное решение: операции сохранения и поиска вынести в отдельную часть приложения, а правила проверки имён и телефонов держать в прикладной части. Эта граница позволит позднее заменить реализацию хранения с меньшим числом изменений в приложении. Архитектура здесь означает распределение ответственности между частями программы.

Предполагаемый путь вызова: визуальный интерфейс или API → правила справочника → операции хранения → SQLite.

В первой итерации нужна только реализация для SQLite. Конкретные интерфейсы в коде, схема таблиц, индексы для ускорения поиска и настройки транзакций будут определены после выбора языка и уточнения требований. Транзакция — группа операций, которая фиксируется целиком или отменяется целиком.

## Risks / Trade-offs

- Разные движки могут по-разному сравнивать текст и обеспечивать сохранность. При замене нужно повторно проверить сценарии из спецификаций; наличие отдельной части для хранения само по себе не гарантирует совместимость.
- Будущий движок может потребовать переноса данных. Формат переноса и совместимость с файлами SQLite сейчас не обещаются.
- Избыточная универсальность увеличит объём учебного проекта. До появления второго движка ограничиваемся простой границей доступа к данным.

## Нерешённые вопросы до завершения проекта решения

Язык, форма визуального интерфейса и API, правила данных, нагрузка и границы надёжности остаются открытыми; см. Q2–Q6 в `review.md`. Ответы могут изменить технический проект и список задач, поэтому план реализации пока не составлен.
