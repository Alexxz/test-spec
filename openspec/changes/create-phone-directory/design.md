# Design

## Context

Первая итерация учебного справочника: Python, SQLite, интерфейс в браузере и HTTP API с JSON. Правила данных и поиска описаны в `specs/`. Собственный движок БД возможен в будущем. Здесь зафиксированы выбранные технические решения для первой реализации; кода пока нет.

## Goals / Non-Goals

- Один пользователь на одной машине, создание записей и точный поиск в обоих направлениях.
- Записи сохраняются между запусками и после аварийного завершения процесса.
- Проверочный объём — 10 000 записей, отображение результата поиска — за одну секунду по методике ниже.
- Собственный движок, изменение и удаление записей, доступ через Интернет, резервное копирование и перенос между движками не входят в первую итерацию.

## Decisions

### D1: SQLite и транзакции

Используем Python со стандартным модулем `sqlite3` и файловую SQLite. Путь к файлу задаётся настройкой приложения и остаётся тем же между запусками; база в памяти не подходит. При первом запуске создаём файл и схему, при последующих — открываем существующие данные без пересоздания.

Новый файл получает `PRAGMA application_id=0x50484431` и `user_version=1`. Существующий файл до обслуживания HTTP проверяется на эти маркеры и ожидаемую схему: таблицу records, типы и обязательность колонок, первичный ключ, BINARY-сравнение и неуникальные индексы имени и телефона. Несовместимый, пустой, повреждённый либо чужой существующий файл отклоняется понятной ошибкой запуска. В него не выполняются команды создания или изменения схемы и настроек; файл не удаляется и не заменяется. Проверка не запрещает штатное восстановление SQLite по собственному журналу после сбоя. Автоматической миграции или «починки» чужой схемы нет. Создание схемы и маркеров нового файла выполняется одной транзакцией.

Создание записи выполняется в транзакции — группе операций, которая фиксируется целиком или отменяется целиком. Ответ об успехе отправляем только после успешного `commit` (фиксации). Используем журнал `DELETE` и `synchronous=FULL`; настройки проверяются при открытии соединения. На каждый запрос открываем отдельное соединение и закрываем после завершения, включая ошибку. При ошибке записи откатываем транзакцию и возвращаем ошибку API.

Первая версия покрывает сбой процесса на исправном диске. Отключение питания, повреждение носителя и восстановление из резервной копии не входят в проверяемые гарантии. Для операции с потерянным ответом допускается наличие целой записи: автоматический повтор создания не выполняется, поскольку дубликаты разрешены.

Альтернатива — сразу собственный движок — отложена. SQLite позволяет сначала проверить прикладное поведение.

### D2: Граница хранения и схема

Путь вызова: браузер или программа → HTTP API → правила справочника → операции хранения → SQLite.

Часть хранения предоставляет три операции: создать запись, найти по имени, найти по телефону. Проверка типов, удаление окружающих пробелов U+0020 и правила полей находятся в прикладной части. Проверка имени использует `any(not char.isspace() for char in name)` после `strip(" ")`, телефона — `re.fullmatch(r"[+]?[0-9]{1,15}", phone)` после той же обрезки. Это не литерал JSON с дополнительным экранированием. SQL остаётся внутри реализации хранения; это позволяет позже заменить её, повторно проверив те же сценарии. Несколько движков одновременно в первой версии не поддерживаем.

Таблица `records`: `id INTEGER PRIMARY KEY AUTOINCREMENT`, `name TEXT NOT NULL COLLATE BINARY`, `phone TEXT NOT NULL COLLATE BINARY`. Идентификатор возвращается наружу как непрозрачная строка: клиент не должен вычислять следующий ID или придавать ему смысл. Отдельные неуникальные индексы по имени и телефону ускоряют точный поиск. Ограничения уникальности пары нет.

Поиск использует равенство с `BINARY`, без `LIKE`, изменения регистра или Unicode-нормализации. Две визуально одинаковые строки с разными последовательностями Unicode считаются разными. Все значения передаются SQL-параметрами, а не вставляются в текст запроса. Порядок результатов не является контрактом. Все совпадения возвращаются одним списком, без скрытого ограничения и разбиения на страницы.

### D3: Python, Flask и браузер

Выбран Flask — библиотека для обработки HTTP-запросов и выдачи веб-страницы. Интерфейс — обычные HTML, CSS и JavaScript без отдельной сборки. Альтернатива с отдельным приложением интерфейса добавила бы второй набор инструментов без необходимости для текущего объёма.

Один процесс обслуживает страницу и API по одному адресу, слушает `127.0.0.1`; порт по умолчанию 5000, задаётся настройкой. Отладчик отключён. Первая версия предназначена для локального учебного запуска. Сетевой доступ и учётные записи требуют отдельного изменения требований.

На странице есть форма создания, выбор поля поиска, строка запроса, список результатов и область сообщений. Браузер использует тот же API, что и программы. Пользовательский текст выводится как текст, а не исполняемый HTML. Подсказки до отправки объясняют формат телефона и точное сравнение имени с учётом регистра. Результаты представлены обычным выделяемым текстом, чтобы номер можно было скопировать.

Создание и поиск имеют состояния ожидания, выполнения, успеха и ошибки. На время операции блокируется повторная отправка соответствующей формы, но не другой формы. При ошибке поля сохраняются, после завершения кнопка снова доступна. Успех создания показывает фактически сохранённые значения. При новом поиске старые результаты скрываются сразу; ответ связывается с отправленными значениями запроса.

Для обоих запросов браузер задаёт срок ожидания 5 секунд через AbortController; это выбранное техническое значение для выхода из зависшего состояния, а не замена критерия успешного поиска за одну секунду. Отмена ожидания в браузере не гарантирует отмены операции на сервере. При сетевой ошибке или истечении срока создания интерфейс сообщает, что исход неизвестен, и предлагает проверить запись поиском; автоматически запрос не повторяет. После ошибки поиска сообщает о недоступности операции, а не об отсутствии совпадений.

Если до операции такая же пара уже существовала, её наличие в поиске не доказывает успех последнего POST. Не обещаем гарантированно однократное создание при потере ответа: ключи идемпотентности и дедупликация операций в первой версии отсутствуют. Блокировка формы предотвращает повторное нажатие при ожидании, но не меняет разрешение на явные дубликаты.

## Файлы и границы реализации

Это план будущих файлов, а не существующий код. Минимальная версия Python — 3.12; конкретные версии библиотек фиксируются при установке и проверке окружения.

| Файл | Ответственность |
| --- | --- |
| `pyproject.toml`, `requirements.lock` | Метаданные, зависимости и зафиксированные версии, включая инструменты проверок |
| `phone_directory/__main__.py` | Аргументы запуска, проверка хранилища, запуск локального HTTP-сервера |
| `phone_directory/domain.py` | Record, ошибки, проверка ввода, операции справочника и протокол хранения |
| `phone_directory/sqlite_store.py` | Инициализация и проверка схемы, соединения, SQL и транзакции |
| `phone_directory/web.py` | create_app, страница и обработчики HTTP, преобразование ошибок в JSON |
| `phone_directory/templates/index.html` | Формы, подсказки и области результатов и сообщений |
| `phone_directory/static/app.js`, `phone_directory/static/style.css` | Обращения к API, состояния интерфейса, отображение и оформление |
| `tests/test_domain.py`, `tests/test_storage.py`, `tests/test_api.py` | Правила, сохранность и HTTP-контракт |
| `tests/test_journeys.py`, `tests/test_performance.py`, `tests/conftest.py` | Браузерные пути, измерения и общие тестовые настройки |
| `README.md`, `reports/` | Инструкция запуска и результатов проверок, отчёты приёмки |

В доменной части неизменяемый `Record(id: str, name: str, phone: str)`; результат поиска — `list[Record]`. Протокол `RecordStore` задаёт `create(name: str, phone: str) -> Record`, `find_by_name(name: str) -> list[Record]` и `find_by_phone(phone: str) -> list[Record]`. Он принимает уже проверенные и обрезанные значения. Реализация SQLite преобразует ошибки SQLite в `StorageError`; она не формирует HTTP-ответы.

Прикладная часть `DirectoryService(store: RecordStore)` предоставляет `create(name: object, phone: object) -> Record`, `find_by_name(name: object) -> list[Record]` и `find_by_phone(phone: object) -> list[Record]`: тип object позволяет явно проверить неверные значения из JSON. Проверка запроса HTTP (поля, параметры, тип тела) остаётся в web.py; проверка значений — в сервисе. Неверные значения дают `ValidationError`; ошибки обеих категорий не возвращаются как пустой список.

Фабрика `create_app(db_path: pathlib.Path)` в web.py возвращает Flask-приложение после инициализации либо проверки БД. В sqlite_store.py за это отвечает `initialize_or_validate(db_path: pathlib.Path) -> None`; при ошибке запуска процесс завершается до открытия порта. Необходимые `__init__.py` добавляются при создании пакета.

Команда запуска: `python -m phone_directory --db ./data/phone-directory.sqlite3 --port 5000`. Эти значения используются по умолчанию. Относительный путь разрешается от текущего каталога; абсолютный путь выводится при запуске. Для нового хранилища недостающий родительский каталог создаётся; ошибки доступа завершают запуск. Браузерная страница доступна через `GET /`. В README поясняется: другой путь создаёт другой справочник. Для проверок фабрика получает временный путь; рабочий пользовательский файл не используется.

## HTTP API

Контракт — точное описание допустимых запросов и ответов, на которое могут опираться клиенты.

| Операция | Запрос | Успешный ответ |
| --- | --- | --- |
| Создание | `POST /api/records`, JSON-объект с полями `name` и `phone` | `201`, объект записи |
| Поиск по имени | `GET /api/records?name=...` | `200`, объект с полем `items`, содержащим список записей |
| Поиск по телефону | `GET /api/records?phone=...` | `200`, объект с полем `items`, содержащим список записей |

Объект записи: `{"id":"1","name":"Анна","phone":"+79991234567"}`. Пустой результат: `{"items":[]}`. Строки передаются в Unicode через JSON, ответы API имеют тип `application/json`.

Для POST обязательны только два строковых поля `name` и `phone`; лишние поля отклоняются. Неверный JSON, неверная форма тела и нарушение правил полей возвращают `400`. Тело не с типом `application/json` возвращает `415`. В GET обязателен ровно один параметр `name` или `phone`, ровно с одним значением; отсутствие, повтор, оба параметра или посторонние параметры возвращают `400`. Клиент кодирует параметры URL, включая `+` как `%2B` (в браузере — через `URLSearchParams`).

Форма ошибки: `{"error":{"code":"validation_error","message":"Понятное описание"}}`. Код предназначен программе, сообщение — человеку.

| HTTP-статус | `error.code` | Значение |
| --- | --- | --- |
| `400` | `validation_error` | Неверные входные данные |
| `415` | `unsupported_media_type` | Неверный тип тела POST |
| `503` | `storage_error` | Не удалось обратиться к хранилищу или сохранить запись |
| `404` | `not_found` | Неизвестный адрес API |
| `405` | `method_not_allowed` | Метод не поддерживается по этому адресу |
| `500` | `internal_error` | Непредвиденная ошибка приложения |

При потере ответа на POST клиент не должен считать повтор безопасным: исходная операция могла завершиться, а повтор может создать вторую запись. Это предупреждение включается в документацию рядом с примером создания.

Ошибки на адресах `/api/` также возвращаются в JSON. Ошибка хранилища не раскрывает SQL, пути файлов или трассировку стека в ответе. В API нет операций изменения и удаления. Отсутствие совпадений — успешный `200`, а не `404`.

## Проверка производительности

Это выбранная методика приёмки, а не уже выполненное измерение. Ориентир пользователя — тысячи записей; для проверки выбран набор 10 000. Число не является пределом хранения.

Эталон: локальная Linux-машина или виртуальная машина с двумя доступными процессорными ядрами, 4 ГиБ RAM и SSD, приложение и браузер на одной машине, один пользователь без параллельных запросов. В отчёте фиксируем модель CPU, ОС, RAM, носитель и версии Python, SQLite и браузера; вывод относится к этому окружению.

Данные: 10 000 записей с именами длиной до 100 символов Unicode и телефонами до 15 цифр с необязательным плюсом. В основной набор включаем уникальные значения, имя с 100 совпадениями и телефон со 100 совпадениями. Для последнего случая используем отдельный набор того же объёма, в котором все имена одинаковые. Это условия измерения, не ограничения входных данных.

После запуска и после смены набора прогреть приложение десятью поисками. Затем выполнить по десять последовательных поисков для шести случаев: уникальное имя, уникальный телефон, отсутствующее имя, имя со 100 совпадениями, телефон со 100 совпадениями, имя с 10 000 совпадениями. Измерять браузерной автоматизацией от отправки формы до появления всех строк и завершения следующего кадра отрисовки. Каждый из 60 поисков должен занимать не более 1 000 мс; записать все измерения и максимум. API отдельно проверяется на полноту результатов, чтобы быстрый ответ за счёт потери записей не прошёл приёмку.

Если критерий не выполнен, сначала измерить причины и оптимизировать. Изменение критерия или введение разбиения на страницы требует явного пересмотра спецификации.

## Проверка критических пользовательских путей

Пути и связь с требованиями описаны в `critical-user-journeys.md`. Приёмка проходит через запущенное приложение с реальным файлом SQLite: успешный путь создания, оба поиска, повторный запуск, затем проверка прежних значений и ID. Браузерные проверки охватывают ошибки ввода, пустой результат, ошибку хранилища, потерю ответа и продолжение работы после восстановления.

Для воспроизводимой потери ответа в проверке CUJ-3 сначала дать серверу завершить запись, затем скрыть ответ от браузера средствами тестового перехвата. Проверить сообщение о неопределённости, отсутствие второго POST и наличие целой записи в поиске. Отдельно имитировать истечение срока ожидания и убедиться, что форма снова доступна. Для этого тестового случая пара до запроса отсутствует; ограничение для уже существующей пары проверяется по документации, а не подменяется обещанием безопасного повтора.

Для CUJ-1 проверить последовательность «успешный поиск → новый запрос → ошибка»: прежний результат не должен оставаться под новым запросом. Затем восстановить доступность и повторить запрос с сохранённым вводом. Для CUJ-3 задержать ответ и нажать сохранение повторно, убедившись, что сервер получил один POST. Все задержки и сбои организуются тестами, без добавления рабочих HTTP-адресов для инъекции ошибок.

## Проверка сохранности

- Штатно остановить и заново запустить приложение с тем же файлом, проверить значения и ID всех подтверждённых записей.
- В отдельном дочернем процессе подтвердить создание, завершить процесс через `SIGKILL`, перезапустить и проверить запись.
- Управляемо остановить процесс после вставки до фиксации, а также после фиксации до ответа. После перезапуска допустимы только целая запись или её отсутствие; прежние записи сохраняются. Точки остановки используются в тестах хранения и не доступны через рабочий API.
- Вызвать реальную ошибку SQLite `SQLITE_FULL` через ограничение `max_page_count` в отдельной тестовой БД, проверить отсутствие подтверждения успеха. После снятия ограничения проверить прежние записи и возможность продолжить запись. Отдельно проверить HTTP-преобразование ошибки в `503`.

## Risks / Trade-offs

- Собственный движок может иначе сравнивать текст и обеспечивать сохранность → повторно выполнить сценарии спецификации; перенос существующих данных планировать отдельно.
- Возврат всех совпадений может замедлить браузер → проверить случай с 10 000 совпадениями, не подменять полноту результатов незаявленным ограничением.
- Успешная фиксация с потерянным ответом создаёт неопределённость для клиента → не повторять POST автоматически, объяснить пользователю возможность проверить поиском.

## План первого запуска

Создать окружение, установить зафиксированные зависимости, выбрать путь файла и запустить приложение. Пошаговые команды должны появиться в README при реализации и быть проверены на чистом окружении. При ошибке запуска существующий файл не пересоздаётся и не удаляется. Миграций существующей схемы пока нет, поскольку существующей реализации нет.
