# ADR-0002: Отделение правил справочника от хранения

Дата оформления: 2026-10-25. Статус: **Принято**.

Происхождение: техническое решение автора при детализации перспективы собственного движка; зафиксировано в design.md и проверено в Elephant + Goldfish. Пользователь не задавал конкретных интерфейсов модулей.

## Контекст

SQLite выбрана для первой версии, а собственная реализация хранения возможна позднее. Правила имени, телефона, дубликатов и точного поиска должны оставаться понятными независимо от SQL и веб-интерфейса.

## Решение

Разделяем HTTP-обработчики, прикладные правила и доступ к данным. DirectoryService проверяет значения и вызывает RecordStore с тремя операциями: создание, поиск по имени и поиск по телефону. Реализация SQLite отвечает за SQL, соединения и транзакции; она возвращает записи или ошибку хранения, а не HTTP-ответы.

В первой версии создаём одну реализацию хранения и тестовую подмену для проверки прикладных правил. Подмена — простая реализация интерфейса для теста, не второй рабочий движок. Подробные сигнатуры и типы находятся в design.md.

## Альтернативы

- **SQL прямо в HTTP-обработчиках:** меньше начальных границ, но правила, веб-протокол и хранение оказываются связаны.
- **Универсальный слой для множества БД:** расширяет интерфейс под неизвестные будущие потребности. Сейчас достаточно трёх требуемых операций.

## Последствия

Правила можно проверить без дисковой БД, а SQLite — отдельно от HTTP. Цена — дополнительный интерфейс и преобразование ошибок между частями приложения.

Граница уменьшает связанность, но не гарантирует замену движка без изменений. Новый движок должен обеспечить ту же семантику поиска, ID и сохранности; перенос файлов решается отдельно.

Уменьшение объёма изменений при будущей замене — ожидаемая польза архитектурного выбора. Её ещё нельзя подтвердить опытом второй реализации: такой реализации нет. См. [различие решений и фактов](../../openspec/changes/create-phone-directory/fact-grounding.md#как-читать-результат).

## Когда пересмотреть

При добавлении изменения или удаления записей, новых видов поиска либо второй рабочей реализации хранения. Расширять интерфейс следует под согласованное поведение, а не под гипотетические возможности БД.
