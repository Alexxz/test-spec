# ADR-0006: Однострочное имя с одинаковой проверкой в браузере и API

Дата оформления: 2026-10-25. Статус: **Принято**.

Происхождение: LLM-expert review выявил несоответствие между широким допустимым именем и поведением обычного поля браузера. Пользователь попросил сохранить за ним роль дилетанта в учебном проекте. Конкретное поведение выбрал автор: имя в одну строку без управляющих символов. Это уточнение прежних правил, а не прямой выбор пользователем диапазонов Unicode.

## Контекст

Ранее имя с буквами и переводом строки либо табуляцией было допустимо. При точном поиске каждый символ имеет значение. Обычное поле text удаляет CR и LF по правилам HTML, поэтому могла сохраниться или искаться другая строка, чем та, которую пользователь вставил. [HTML: Text state](https://html.spec.whatwg.org/multipage/input.html#text-(type=text)-state-and-search-state-(type=search)).

## Решение

В первой версии имя и запрос поиска по имени должны быть однострочными. Отклоняем U+0000–U+001F, U+007F–U+009F, U+2028 и U+2029, включая табуляцию и перевод строки. Применяем одну проверку в сервисе для браузера и API. Проверка браузера дополнительно отклоняет вставку с такими символами до изменения поля; она не заменяет серверную проверку.

Окружающие U+0020 по-прежнему обрезаются. U+00A0, внутренние пробелы, регистр, буквы разных языков и корректные дополнительные символы Unicode сохраняются. Непарные суррогаты отдельно отклоняются как некорректные строковые значения.

## Альтернативы

- **Сохранить многострочные имена:** потребует отдельного решения о полях ввода, преобразовании переводов строк и копировании для точного поиска. Для имени в первой версии это лишняя сложность.
- **Молча удалить управляющие символы:** может превратить одно имя в другое и скрыть ошибку вставки.
- **Проверять только браузер:** оставит другой контракт для программного клиента.

## Последствия

Пользователь видит понятное правило и сообщение об ошибке. API отклоняет строки, которые прежний черновик разрешал; соответствующий сценарий обновлён. Развёрнутых данных и клиентов пока нет, поэтому миграция первой версии не требуется.

## Когда пересмотреть

При реальной потребности в многострочных отображаемых именах или иных форматах контакта. Такое расширение должно определить одинаковое представление данных во всех клиентах и новые сценарии точного поиска.
